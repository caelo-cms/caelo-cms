# Reporting jobs

Issues #1359, #1360, #1574 and #1646 (#1140 category A). The admin only does work inside a request (CLAUDE.md §11.B Tier 5). Periodic work runs on the [scheduler tick](./scheduler-tick.md). Long, bounded work that one request cannot hold runs in a **reporting job**: a container job of its own that the admin starts once per piece of work and that reports back to the admin by request. Each report is a request, so it brings the CPU the admin needs to answer and record it. Nothing waits on an idle admin instance.

Five kinds run this way: the quality audit after a Stage (#1359), a site import's crawl (#1360), the build carrier (#1574), whose one report holds the request a build runs in, a Stage's plugin collection index (epic #1644, #1648) and a plugin's batch run (#1646).

## One attempt

1. **Start.** The admin mints a token (32 random bytes) and records the attempt with the token's SHA-256 and a first lease (`reporting_jobs.begin_attempt`). It then launches the attempt. On Google Cloud that is one execution of the kind's Cloud Run job. The order (kind, work id, attempt, token, the admin's URL, the admin's version) travels as an env override. The quality audit starts in the Stage request, right after the build is recorded (`deploy.trigger`), and after `quality_audits.retry`. A site import's crawl starts in the request that started it (`imports.create_run` on Settings → Import) or approved it (`imports.execute_proposal`).
2. **Reports.** The job sends one JSON POST per step, for example `start`, `source` or `result` for the audit. Every admitted report extends the lease. A heartbeat renews it while the job works (`run-job.ts`, the one interval a job keeps). An input over 1 MiB of JSON travels first in parts (`upload-part`, at most 128 parts of 1 MiB characters each, so a part stays under the request cap whatever its characters). The action then names the upload. The admin reads an upload once, also when the action then fails, so the parts and their action are one report under one retry budget: a retry that finds the parts gone sends them again under the same upload id (a part sent again replaces itself), and the failure the budget ends on is the action's own. Answers stream, so a large read such as a big site's page index is not limited by a response size.
3. **End.** The action that ends the work (`result`, or `start` answering "nothing to do") finishes the row. From then on every report of the work gets `409`, and the job stops.

On another version than the admin that started it (an upgrade moved the admin first), the job sends `defer`: the lease ends at once, and the next tick starts the next attempt on the job's image as it is then. An order from an admin on another version is read without the fields this job does not know yet (`parseJobOrder`), so a newer order defers instead of failing its schema; on the job's own version an unknown field is still a malformed order.

A job also gives its attempt back (`deferAttempt`) when the admin could not answer one of its reports in time: the reporter's retries ran out on a 429, a 5xx or an unreachable admin, or a findings check stopped waiting for a read that was still running (`faultWatchingReporter` sees both, also when a check swallowed the error, and the audit lets every read end before it decides). Nothing the delay spoiled is recorded; after the last attempt the work fails with the reason.

### Helpers: more tasks for one attempt

An attempt runs one task of its own, its lead. Elastic work (a search index, a plugin batch in pieces) gets more tasks from the job capacity ledger ([job-capacity.md](./job-capacity.md), #1776): while CPU is free, the admission starts helpers, further executions of the same Cloud Run job for the attempt that runs, each with `taskCount` of its own. A helper's order names its booking (`helper`) and carries a token of its own, which `reporting_jobs.authorize` admits for its attempt while its booking holds it; its reports and heartbeats keep its booking's lease, its `defer` gives back only its own task, and it reports no result. Every task claims pieces of the work from the admin (`job_pieces.claim`), so tasks may join and leave at any time: a helper ends when no piece is left for it, or after its piece when a job of a higher class needs the CPU. A new attempt drops the helpers of the attempt before. Inside the admin (self-hosted) elastic work runs on its lead alone. No job definition carries a fixed `parallelism`: Cloud Run refuses to create one whose parallelism times its CPU exceeds the project's quota (#1764).

## The backstop

A job that dies stops reporting. Its lease runs out: 15 minutes for the first report, then 5 minutes (the audit) or 10 minutes (the crawl) after every later one (`JOB_TIMING`). The core task `core:reporting-jobs` runs on every tick and does two things per kind:

- It starts the next attempt of every job whose lease ran out, with a new token. The old attempt's reports then get `409 stale`. After the kind's last attempt (3 for the audit, 5 for the crawl) it gives the work up: the audit is recorded as `errored` with code `job-failed`, the import run as `failed`, and the message names where the last attempt ran.
- It starts a job for work that has none: an audit or a crawl whose start was lost, or one a release before the kind's job left running (`quality_audits.sweep_unstarted`, `imports.sweep_unstarted_crawls`: a crawl of the old in-admin worker once its heartbeat is 15 minutes old).

Then, once for all kinds, it gives back the CPU of executions that stopped without a word and runs the capacity ledger's admission: jobs that waited for CPU start, and elastic work gets its helpers ([job-capacity.md](./job-capacity.md)).

Every start books its work in the ledger first: an immediate kind always starts, a kind that may wait (the search index, a plugin batch) waits there with its reason and starts when the admission says so. A launch that fails (Cloud Run refused it) releases the lease at once, so the next tick tries again. An install that cannot run the job at all (aws and azure until #749 / #750, a Google Cloud admin without the job's env) records the work as failed with the reason. It never runs the work inside the admin instead.

## Who may report, and what a report can do

Two checks, both required:

1. **IAP identity.** On Google Cloud the job signs a JWT as its own service account for exactly the admin's origin (`aud = <origin>/*`, IAM `signJwt`, the path the scheduler and caelo-mcp take) and passes the admin's IAP. The endpoint takes a report of a kind only when IAP's signed assertion names that kind's account (`CAELO_AUDIT_RUNNER_SERVICE_ACCOUNT` for the audit, `CAELO_IMPORT_CRAWL_SERVICE_ACCOUNT` for the crawl): the crawler cannot report for an audit, nor the audit runner for a crawl. An admin without that variable takes no report over HTTP: its jobs run inside it.
2. **The attempt's token** (`x-caelo-job-token`), compared as SHA-256 with the current attempt's. A per-minute cap (600) refuses a runaway job with `429`.

A report runs only its kind's actions, as the system actor, on its own work. The audit can read the check sources of the main line, ask an active plugin's audit operation, and record its own result through `quality_audits.record_result`. The crawl can ask for renders of its run and record its run's pages, captures, notes and end, nothing else (below). Nothing in a report builds or publishes anything (CLAUDE.md §2, one path to live). What follows an audit, such as the chat's card or the gate of Publish live, reads the recorded result as before.

### Threat model

- **A compromised job** can do what its reports allow for its own run: read what its kind reads, and report a wrong result for it. For the audit that is a wrong quality verdict on one Stage: a gate that opens when it should not, or findings that prompt the fix loop. For the crawl it is wrong content in one import run, which a person or the AI reviews before anything of it becomes a page, and renders within the run's budget. Publish live stays a human's click either way. It cannot reach another run (the token), another kind (the identity), or anything else of the admin: IAP lets the account in, but every other route still needs a session, the internal token or the scheduler's identity, and the job has none of them. It holds no database credential and no secret.
- **Reports are untrusted data.** A job is the admin's own code, but it reads what it reports from pages it fetched: the staged build for the audit, third-party sites for the crawl (#1360). So every report is validated at the boundary (the envelope, the token, the action's Zod schema, the size caps), stored through the same ops as before, and rendered as text.
- **Why these jobs pass IAP when the capture job must not.** The capture job (#1217) renders untrusted pages in a full browser, which is the classic exploit surface, so it has no IAP access at all: a browser exploit there reaches nothing but the internet it already renders. A reporting job runs no browser and executes nothing it fetches; it parses fetched bytes as data. The audit runner hands every browser run to the Lighthouse tasks; the crawl asks the admin for every render, and the admin starts the capture job. Those tasks keep their identities without IAP access, and the crawl never touches the capture job or its bucket. The rule: **IAP access goes only to job identities that run no browser and execute nothing they fetch.**
- **A job that wants more tasks.** A job only says how many tasks its work would use (`pieces`, capped by its kind's `maxTasks`); the admin decides how many helpers it gets out of the budget (job-capacity/plan.ts), and every start of helpers is audited (`job_capacity.admit`). A runaway or compromised index job can therefore cost at most its work's cap of tasks while CPU is free, each bounded by `maxRunSeconds` (6 hours for the index); helpers stop after their piece when a job of a higher class needs the CPU, and a helper token admits only its own attempt's reports. It gains no other right.
- **The token in the execution's env.** A principal that may read the execution (`run.executions.get`) can read the token. It cannot use it without passing IAP as the job's account, which takes `serviceAccountTokenCreator` on that account (the account itself and project owners). A token is good for one attempt of one run, and a newer attempt replaces it.

## The quality audit as a reporting job (#1359)

The job `caelo-<env>-audit-run` runs the admin image's `reporting-jobs/job-entry.ts` as `caelo-<env>-audit-run@`. It holds:

- `roles/iam.serviceAccountTokenCreator` on itself, so it can sign its IAP credential;
- `roles/iap.httpsResourceAccessor` on the admin. The operator-access sync keeps it there through `CAELO_OPERATOR_ACCESS_IAP_SERVICE_ACCOUNTS`;
- `roles/logging.logWriter`;
- `roles/storage.objectViewer` on the staging bucket, to serve the staged slot to its findings checks, and on the audit-results bucket, to read the Lighthouse results;
- `roles/run.jobsExecutorWithOverrides` and `roles/run.viewer` on the Lighthouse job `caelo-<env>-audit` (#875), whose tasks it starts.

No secret, no Cloud SQL, no VPC. `REPORTING_JOB_FORBIDDEN_ROLES` names the line, and `reporting-job-setup.test.ts` asserts every grant. The admin's run SA may run the job with overrides and read its executions. The upgrader has actAs on the account, because every app-roll moves the job's image with the admin's.

The audit itself is the same code as before (`quality/audit-run.ts`), now fed by reports (`quality/audit-job.ts`; admin side `quality/audit-job-kind.ts`):

| Report | The admin answers with |
|---|---|
| `start` | `quality_audits.claim`: the run to audit (its pages, the staged slot), or "stop" when a newer Stage superseded it |
| `source` | one read of a findings check: modules, layouts, the page index, redirects, the site's URLs, link issues |
| `plugin-findings` | one call of an active plugin's `auditFindingsOperation` (the batching runs in the job, `collectPluginFindings`, up to 4 batch calls at once; on a batch call with only its own pages the admin adds the audit run as `auditRunId`, #1721) |
| `result` | `quality_audits.record_result` |

## The site import's crawl as a reporting job (#1360)

The job `caelo-<env>-import` runs the same entry point as `caelo-<env>-import@`. It holds the shared line and nothing else: `roles/iam.serviceAccountTokenCreator` on itself, `roles/iap.httpsResourceAccessor` on the admin, `roles/logging.logWriter`. No bucket, no other job, no secret, no Cloud SQL, no VPC (`importCrawlJobSpec`; `reporting-job-setup.test.ts` asserts it).

The crawl is the same code as before (site-importer `crawlSite`), driven by the job (`site-import/crawl-job.ts`; admin side `site-import/import-job-kind.ts`, wire in `import-job-wire.ts`):

- **In the job:** the crawl loop, link discovery, extraction, and its own fetches of robots.txt and sitemaps (and of a page whose render failed), every one through the SSRF guard (site-importer `safe-fetch.ts`) with the admin's exemptions (`CAELO_IMPORTER_ALLOWED_HOSTS`, sent with `start`). It runs no browser and executes nothing it fetches.
- **In the admin, per report:** each page's render, through the install's renderer (the capture job on Google Cloud, the one shared browser on a self-hosted admin) behind the same guard. The admin stores the screenshot under the run's prefix and answers with the HTML and the style samples; the pixels never travel to the job and back. A render the admin reports as failed falls back to the job's own static fetch, as before; a render the admin cannot be asked for (unreachable or busy past the retries, refused) stops the attempt instead, so no page is kept without its JavaScript-built content. The stop reaches the crawler as an abort signal: no worker takes another URL or waits out the throttle for one, so the attempt does not walk its frontier first. A passing fault gives the attempt back; a refusal fails the run with its reason.

| Report | The admin |
|---|---|
| `start` | `imports.claim_crawl`: source, depth, page cap, LIST mode's URLs, the scope, the stored checkpoint. A malformed list or scope fails the run (no fallback) |
| `render` | `imports.take_render` (the run must be crawling, at most `3 × page cap + 50` renders), then renders and stores the screenshot at `import-screenshots/<run>/src-<sha256(url)>.png`. Past the budget it answers `budget`: the job then takes no next URL, finishes with the pages it has and records every URL left in the skip ledger (redirects, duplicates and non-HTML pages are rendered too, and do not count toward the cap). The job counts the budget itself from `start`, so a well-behaved crawl never meets the answer. `get_import_run_report` states a spent budget from the admin's own counter (`crawl_renders`), because the skip ledger keeps only its first 200 entries |
| `batch` | `imports.write_extracted_pages`, then the captures in one bulk write (`imports.set_page_captures_by_url`): every key must be one of this run's. The run's counts move in the same write as its pages (#1590), so `list_import_runs` shows the crawl's progress: pages extracted grows by the rows the write added (the admin's own count, so a batch sent again adds nothing), pages seen takes the job's count only when it is higher, and never stays below the pages written |
| `checkpoint` | `imports.save_crawl_checkpoint`, after a strict schema with caps |
| `capture-targets`, `page-capture`, `page-note` | the second pass over the pages still without a screenshot (`imports.list_capture_targets`, `imports.update_page_capture`, `imports.add_crawl_page_note`), only for pages of this crawling run |
| `finish` | the run's design tokens from all pages' samples, then `imports.finish_crawl`: ready for review, the run report keeps the error and skip ledger. The report names no page count: the admin counts the run's rows, and pages seen only goes up (#1590) |
| `fail` | `imports.fail_crawl`: only a run that is still crawling |

**Resume.** After every batch the job reports the frontier (compacted: the first entry of each URL it has not seen). A checkpoint counts only pages whose batch was written before it (the crawl streams its pages through `onBatch`); a URL still in flight or a page not yet written goes back to the front of the queue, so a killed job loses no page (site-importer `crawler.ts`, #1360). A new attempt resumes there, and a page whose batch was still in flight is crawled again, its write idempotent (`UNIQUE(run_id, source_url)`).

**The page cap.** A worker takes its slot of the run's page cap when it takes a URL, not when the page is done, so the crawl's parallel workers cannot all take a URL while the count is still below the cap; a URL whose page is dropped (an error, a skip, a redirect duplicate) gives its slot back (#1590).

**Untrusted data, to the end.** What the crawl reports reaches the AI marked as crawled content: `get_import_page` (title, meta description, text, tokens), `read_page_more` and `query_page_html` on such a page, `list_import_pages` (source URLs, the run's error) and `get_import_run_report` (crawl errors, skips, notes, samples) wrap it in `<site-data>` (shared `siteData`), and the static system prompt says what that element means. The tools' own guidance stays outside it.

## The build carrier (#1574)

On request-billed CPU (#1361) a build would freeze the moment the request it runs in ends. A Stage nobody waits for in a request used to go on detached: an agent's `stage_changes` answers "still running" after about 50 s (#1204), and a button's request ends when its browser tab closes. Such a build now runs inside a request a small job holds open, the **build carrier**. The build itself stays in the admin, on its own database and rights; the carrier only carries the request (maintainer decision 2026-11-10; moving the generator into a job is a bigger change, kept for later).

| Piece | Where |
|---|---|
| What to build, as whom, and how it ended (migration 0690) | `build_orders`; ops in `packages/admin-core/src/ops/build_orders.ts` |
| Asking for a carried build, and waiting for it | `packages/admin-core/src/build-carrier/carry.ts` (`carryBuild`, `executeBuild`, `carryStage`) |
| The kind, its one action `run` | `build-carrier/kind.ts`, `build-carrier/run-order.ts` |
| The job's side | `build-carrier/job.ts`: one report, `run` |
| Google Cloud setup | the `build` entry of `packages/provisioning/src/reporting-job-catalog.ts` (job `caelo-<env>-build`) |

**Who carries their build.** An agent's `stage_changes` and `deploy_staging` (Power-MCP, `caelo_chat`, a subagent: no operator browser on the turn), and every button that builds: the editor's Stage, Publish live, publish anyway and production build, the Changes page's Stage, the pages list's Stage and Publish live, Settings → Deployments' build and promote, and the Approve of a deploy proposal or a publish-anyway proposal, on their pending pages and on their approval cards in a chat (`ai/tools/gated-tools.ts`, #1361). The card's turn waits for the build as before, but a tab closed mid-build stops only the turn: on request-billed CPU a build left without any request would stall. The Live Edit chat's own Stage is not carried: it waits inside its turn, and the operator's Stop or a closed tab stops it with the turn (#1204). The tick's plugin-data build runs inside the tick.

**Refused at once, before anything starts.** A carrier job's cold start takes seconds, so the request first checks what the build would refuse at once (`build-carrier/preflight.ts`), in the op's own words or with the same read the op makes: a chat that is not one of the caller's open chats, a target that does not exist, production for anyone but a person, nothing staged to publish, a quality check that keeps Publish live closed, a deploy proposal that is no longer pending, a publish-anyway the failed check does not allow. Such a refusal writes no order and starts no job. The op still checks everything when it runs, so a check missing here costs the wait, never the decision. A Stage's input is checked when its order is written (`build_orders.create`); a Stage takes as many chats as before the carrier.

**One order, one report.** The request that asks for a build writes an order (`build_orders.create`: the Stage's chats, or the op and its input, and the caller's context as data), starts the order's carrier (`startReportingJob` of kind `build`) and waits for the outcome: an agent about a minute in all, counted from its call (the checks, the order and the job's start included), then "still running" with `get_stage_status`; a button until the build ends. A job start that stalls past the agent's wait answers "still running" too, and the order settles without that request: a launch that fails gives it up, a late carrier runs it, and the backstop gives up one whose job never reports. The order's id is the run's id, also for an approved proposal (its claim takes the id the order passes, `runId` on `deploy.execute_proposal` and `quality_audits.execute_proposal`), so `deploy.stage_status` shows the Stage as queued before its run row exists, and a give-up fails the right run. Only a Stage or a staging build reads as a Stage there; a production build never does. The waiting request looks at its order with a back-off, from 250 ms up to every 5 s. The carrier sends one report, `run`. The admin takes the order (`build_orders.claim`, once), runs the build inside that request as the caller (the ops' own checks decide as in the caller's request: a human for production, its permissions), records the outcome (`build_orders.finish`, tried again for about 10 s while the request still carries it) and answers. Whichever admin instance takes the carrier's request runs the build. The claim logs how long the order waited for its carrier (`[build-carrier] <id>: its carrier took the <kind> order <ms> ms after it was written`): the job's real start time, cold or warm.

**Without a carrier.** A Google Cloud admin whose converge did not set the carrier up (`CAELO_BUILD_CARRIER_JOB` or `CAELO_ADMIN_URL` missing), and AWS and Azure (#749 / #750), have none. A button whose request waits builds in that request, as before the carrier, and says so: the answer carries a warning ("This build ran inside your request, not in a build carrier …"), which the editor shows as a toast, with the upgrade step on Google Cloud (`cms-provision upgrade`, its step "Ensuring the build carrier"). An agent, whose call ends within a minute, is refused before anything is built, with that step: a build in its call would stop when the call ends.

**A long report.** `run` is a long action (`ReportingAction.long`). Once admitted, the endpoint answers at once with a `200` stream that sends a newline every 15 s (`KEEPALIVE_SECONDS`), so nothing between the job and the admin closes the request as idle, and ends with the answer's JSON (leading whitespace is valid JSON). A refusal's status rides inside the answer (`status`), and the job's transport reads it, so a 500 there is still a passing fault. The job waits up to `JOB_TIMING.build.reportTimeoutSeconds` for it, and the job's heartbeat keeps the lease while it waits.

**When the request can no longer carry the build, it stops, with the reason.** The build's signal (passed on to every op it runs, an approved rollback's `deploy.rollback` included) aborts when the carrier's request ends first (the job died, its connection dropped); when its run time is up (on Google Cloud 58 minutes, two before the admin's 3600 s request limit, so the build is never cut off silently mid-way); or when it is asked to stop through its order (`build_orders.request_stop`, with the reason the stopped run then names). The running build looks at its order every 5 s (`stop-watch.ts`): one primary-key read, light enough for the smallest database (#1392). Only the operator's Stop is passed on (`operatorStopOf`): a caller whose request merely ended, such as an MCP client that gave up waiting, leaves the build to its carrier. A stopped build ends as its op ends on an abort: the generator is killed, nothing more is published, and the run is recorded as failed with the reason. Publishing itself stays the op's own step, so nothing is left half-published.

**One attempt, never late.** A carrier that dies ends its build. Usually at once: its request ends, and the build stops with that reason. For a death the admin did not see, `JOB_TIMING.build.maxAttempts` is 1: when its lease (5 minutes after the last report) runs out, the backstop gives the order up (`build_orders.give_up`). An order ends once, with the outcome its build can no longer change, so the waiting request never reads a failure for a build that then goes live. The give-up ends the order only when no build can still succeed for it: its run ended (the order then says what the run says, a success included: "went through, do not run it again", for a build whose carrier died before its outcome was recorded), its run lost its lease (marked failed with where the carrier ran and the next step: "Stage again", "start the build again", or check what production serves and Publish live again), or it has no run (failed the same way). A run still building is asked to stop instead: it stops at its next look at the order, saying it was given up (not the operator's Stop), and ends the order itself. A run never starts for an order that ended first (`beginRunInTx` refuses its id), and `build_orders.finish` writes only an order not yet ended. The run's start and the give-up take one lock on the order's id (`lockBuildOrderInTx`, a transaction-scoped advisory lock, because only the system actor may lock an order row and the start runs as the caller), held until the start has committed its run: a give-up that comes second waits, sees the run, and asks it to stop. An order no carrier works on any more (`build_orders.list_unstarted`: not ended, no running job, older than 2 minutes) is given up the same way, and one that was never started is never started late (kind.ts `unstarted: "give-up"`): a build a person asked for minutes ago is not run behind their back, and the tick never starts a build (`scripts/no-automatic-production-deploy.test.ts`). A launch that fails fails the order at once, so the person who asked hears it now.

**Where it runs.** Google Cloud: one execution of `caelo-<env>-build` per carried build, 1 vCPU / 512 MiB, task timeout 65 minutes. Self-hosted and development: the same carrier in the admin's process, each attempt at once (`inProcess: "at-once"`; two builds still take their turns at the publish leases), and in a test or a script without a registered launcher too: a build must run when asked. AWS and Azure: no carrier yet (#749 / #750), see "Without a carrier".

**Its identity.** `caelo-<env>-build@` holds the shared grants and nothing else: token creator on itself, IAP access to the admin, log writing. No bucket, no other job, no secret, no database, no VPC (`reporting-job-setup.test.ts` asserts it). It runs no browser and executes nothing it fetches; it fetches nothing at all. A compromised carrier can call `run` for its own order only (the token), which runs the build its caller ordered, once; it can withhold the call, and the order is then given up. It cannot change what is built or as whom: the order is the admin's own record, and the job never sees it.

## The job catalog (#1646)

Every kind is one entry of `REPORTING_JOB_CATALOG`: its admin-core kind, its name (job and account `caelo-<env>-<name>`), the two admin env vars that point at it, its machine and env, the grants it holds beyond the shared line, what must be set up before it, and the CLI's lines for it. Nothing else names a kind: the wizard and the converge set the entries up in catalog order, `adminEnvContract` sets each entry's pair of env vars, `adminImageJobs` moves each onto the admin's new image, and the upgrader gets actAs on each account and checks it in its IAM pre-flight. `scripts/reporting-job-catalog-parity.test.ts` fails when admin-core's kinds (`reporting-jobs/kinds.ts`) and the catalog disagree on a kind or its env var names.

| Kind | Job | Machine | Beyond the shared grants | Set up after |
|---|---|---|---|---|
| `quality_audit` | `caelo-<env>-audit-run` | 1 vCPU / 2 GiB, 60 min | reads the staging bucket and the audit results; starts the Lighthouse job | the Lighthouse audit job |
| `site_import` | `caelo-<env>-import` | 1 vCPU / 2 GiB, 6 h | nothing | |
| `build` | `caelo-<env>-build` | 1 vCPU / 512 MiB, 65 min | nothing | |
| `collection_index` | `caelo-<env>-index` | 2 vCPU / 4 GiB, 60 min | reads and creates files in the staging collection store, nothing of live | the collection stores |
| `plugin_batch` | `caelo-<env>-plugin-batch`, `-m`, `-l` | S 1 vCPU / 2 GiB, M 2 vCPU / 4 GiB, L 4 vCPU / 16 GiB (the size the batch declares, #1776), 65 min | nothing: every storage or collection call of the plugin is a report to the admin | |

`roles/storage.objectCreator` and the `roles/run.` roles are in `REPORTING_JOB_FORBIDDEN_ROLES`: a kind may hold one only on a bucket it names in `writeBuckets` or a job it names in `runJobs`, each with its reason, and the tests pin exactly which kind declares which. The Lighthouse audit job (`audit-job-setup.ts`) and the capture job (`capture-job-setup.ts`) are not reporting jobs and stay outside the catalog: neither passes IAP, and the capture job renders untrusted pages with no read right anywhere.

The plugin batch job is the one that runs plugin code: an Owner-approved artifact, in the Deno sandbox inside the job (no network, no files, no env). The plugin reaches the admin only through the job's host side, report by report, never with the job's credential, so its IAP access is the same line every kind holds.

Self-hosted runs every kind in-process; AWS and Azure record every such run as failed with the gap (#749 / #750), never run it inside the admin.

## Self-hosted and development

There is no extra machine. The admin registers the in-process launcher at boot (`setInProcessJobLauncher`, `hooks.server.ts`). Each attempt then runs the same job main inside the admin process, without the request waiting for it, and one attempt of a kind at a time for the kinds that are `in-line` (`in-line.ts`): two audits at once would share the CPU their Lighthouse runs measure, and two crawls would only take turns at the one shared browser. A build carrier's attempts start at once. An attempt in line keeps renewing its lease. Its reports reach `handleJobReport` directly as text, so they pass the same caps, token check and schemas. The self-hosted admin keeps its CPU between requests. A process that dies mid-attempt leaves a lease that runs out, and the tick restarts the attempt. In a test or a script nothing registers the launcher: work is left for whoever drives it (`__tests__/fixtures/drain-audits.ts`), except a carried build, which runs in-process.

## Adding a kind

1. Add its name to `REPORTING_JOB_KINDS` and its timings to `JOB_TIMING` (`protocol.ts`).
2. Declare its `ReportingJobKindDef`: its actions with their Zod inputs (`long` for one that holds its request while the admin works), `inProcess`, `unstarted`, `listUnstarted`, `giveUp`, its admin env vars. List it in `kinds.ts`.
3. Write its job main (it talks only through its reporter) and list it in `job-mains.ts`.
4. Provisioning: one entry in `REPORTING_JOB_CATALOG` (`packages/provisioning/src/reporting-job-catalog.ts`) with only the grants it needs; the wizard, the converge, the admin's env, the image move, the upgrader's actAs and pre-flight and the operator-access IAP list follow from it. Then a line in the cost table (`wizards/gcp-cost.ts`) and an infra-contract bump (`infra-contract.ts`: the new admin starts a job an older install does not have).
5. Tests: its grants against `REPORTING_JOB_FORBIDDEN_ROLES` (`reporting-job-setup.test.ts`), the catalog's pins (`reporting-job-catalog.test.ts`), the parity test, its actions through `handleJobReport`, and a killed attempt restarted by the backstop.
