# Redirects and global settings: what goes live how

Decision 2026-10-26 (#1140, #1157): nothing reaches production through a build the Owner did not click, and there is no automatic redeploy (#1154). Page content goes live with Stage + Publish live. Decision 2026-11-10 (#1550): so do redirects. A saved redirect is a pending change that the staging site serves within seconds and the live site gets with the Publish live that ships it; Go live now is the one named human path past Publish live. The global settings that are not tied to a page or template are a separate topic: each one either lives at the hosting provider, and is synced there when it is saved, or renders into the page HTML, and goes live with the next Publish live like page content.

## Redirects are draft state

An **address** is a from path, both trailing-slash spellings together: a rule answers its path with and without the slash (`redirectFromPathSpellings`). Each address has a **live state** (a target and status code, or none) and at most one **pending change**: a create, a change or a removal, in state **Draft** (served nowhere, held back by every Publish live) or **Staged** (served by staging, live with the next Publish live). A change's origin is `manual` (a person or the AI chose it) or automatic: `page_move` (a rename, a move, the merge's recompose), `page_delete`, `url_migration`, `revert` or `plugin` (the `international-site` plugin's locale-root redirect). It also records the actor, the chat session (for Undo) and the branch.

Storage (cms_admin migration 0682, cms_public 0683):

- `redirects` — the live state, as before, plus a stored generated `address` column (indexed: a lookup by address must be an index condition under the table's RLS policy, which an expression with `rtrim()` can never be). Only a release writes it (below).
- `pending_redirects` — one row per address (`address` unique: the from path without its trailing slash, `caelo_redirect_address`), `to_path` NULL for a removal, `state`, `origin`, `revision` (bumped on every save, so a confirmation binds a version), `actor_id`, `chat_session_id`, `chat_branch_id`. An automatic change cannot be Draft (a CHECK, and the writer refuses it). Journaled (`pending_redirect`, branch-aware).
- `redirect_release_log` — every write of the live table, per address: `kind` `release` (Publish live, an Owner's production build), `take_over` (first publish of a page), `go_live_now` or `rollback`, the live rules before and after (`before_rules` / `after_rules`, every stored spelling), the change's origin and owner, the run. A rollback reconstructs from it the live state as of any run; nothing is derived from it.
- `published_redirect_changes` (cms_public, written into cms_public_staging only) — the shared draft's Staged changes, next to `published_redirects` (the live rows).

Code: `packages/admin-core/src/redirects/` (`model.ts` the model and views, `write.ts` the one writer of pending changes, `release.ts` the live writers, `lifecycle.ts` Undo, Stage, merge and discard, `build-files.ts` the files a build serves), `ops/redirects.ts` (save, list, state changes), `ops/redirects_release.ts` (release plan, Go live now and its approval), `ops/redirects_pending.ts` (targets on another domain), `packages/shared/src/redirect-release.ts` (the planner the gateway and the admin share).

**Two views.** The live view is the live table. The staging view is the live table with the shared draft's Staged changes applied, minus the ones that wait for their target. `redirects.list` (Settings → Redirects, `find_redirects`) shows every address with its live rule and its pending change; Settings → Redirects badges them Live, Draft, Staged, Change staged and Removal staged.

**One change per address.** A new save replaces the address's pending change, also another chat's or another branch's (CLAUDE.md §2: a write takes the other branch's pending change over, never silently): the result names the rule it replaced and the chat that saved it. A save equal to the live state drops the pending change ("already live as it is").

### Saving

Every save goes through `writeRedirectChanges`:

- **Manual:** `redirects.create` / `create_many` / `delete` / `delete_many` with `goLive: "next_publish"` (default, Staged) or `"later"` (Draft), the AI tools `bulk_create_redirects` / `bulk_delete_redirects` (`goLive` `next_publish`, `later`, `now`) and Settings → Redirects (the form's "With the next Publish live", "Later, keep it as a draft", and "Now, without Publish live" for someone with the Publish live permission on a live site). `redirects.set_changes_state` (`update_redirect_changes`, the row actions) moves a change: include (Draft → Staged), keep as draft (Staged → Draft), discard. A delete acts on every address with a live rule or a pending change, a removal included, so deleting again a rule whose removal is a Draft stages that removal.
- **Automatic, always Staged:** the page-move gateway `applyPathMoveEffects` (slug changes, `move_pages`, `pages.refresh_current_path` and the merge's recompose, `revert_page` / `revert_site`), `pages.delete` with a redirect disposition, an approved URL migration, and a plugin's `redirects.create` (the plugin actor's write is automatic, so the shipped `international-site` plugin did not change). A page change's 301, its chain collapse and the take-over of the rule on its new URL therefore go live with the Publish live that ships the page change (#1521, #1523 item 3). The chain collapse retargets a pending change that points at the moved page in place (`retargetPendingRedirects`): it keeps its state, origin and owner, so a Draft nobody included stays a Draft, and only while it still points at the moved page (a change saved again since the move read it keeps its newer target). A page only a chat's branch holds still writes none (#1517, `branchOnlyPageIds`).
- **Chats:** Undo of a chat removes its pending changes (the manual ones, and the automatic ones its unstaged page writes caused, a delete's 301); the live state is never undone by Undo. A Stage settles the automatic changes of the chats it ships: they belong to the staged state from then on. An isolated branch (an experiment, a site migration) keeps its changes until its Stage merge moves them to the shared draft; discarding it drops them.

### Staging serves the staging view

The projection's immediate `redirects` section publishes the live rows and the shared draft's Staged changes into cms_public_staging on commit, so staging redirects within seconds of a save. The staging gateway (#1330, every provider) applies them against the staged build with `planRedirectRelease`, the same planner Publish live uses. Draft changes are served nowhere. During a rolling update an older staging gateway reads only `published_redirects` and serves the live view.

**A change waits for its target.** A Staged change whose same-site target the build does not serve (after the plan's chain collapse) is left out: the address keeps its live state on staging, and Publish live leaves the change Staged until a build that serves the target goes live. A target on another domain, under `/api/` or a 410 never waits. A target with a query or fragment ends the chain collapse, but the serving layers match a rule by its path, so `/alias?utm=x` is served when the rule on `/alias` reaches a served target (`redirectsToUnservedPaths`). **An automatic removal waits for its page:** a page that moves onto an address takes it over from the rule there, and that removal goes live with the build that serves the page at the address, so the rule keeps answering instead of a 404 in between. Leaving a change out can make another chain end at an unserved target, so the planner repeats until nothing more is left out.

### What goes live, and how

The live table changes in exactly four ways, each a function of `redirects/release.ts` that first locks the `live-release` lease row for the rest of its transaction (`lockLiveRedirectWrites`), so two live writes never interleave; `scripts/no-draft-live-writes.test.ts` pins their callers.

- **Publish live** (`deploy.promote`). Before it takes the live-release lease it plans (`redirects.release_plan` against the staged run it copies). The editor's confirmation (`GET /api/redirects/release-plan`, `StageDeployButton`) lists the changes going live, waiting for their target and staying in Draft, and posts the going-live list (`redirectChanges`, each id with its revision). A change saved again after the confirmation has a new revision and waits for the next Publish live, the way a Stage binds its classified snapshot headers. Right before the release is recorded, under the live-release lease, the listed changes are planned again (a change kept as a draft or discarded meanwhile drops out, and so does every change whose chain now ends at an unserved target), and `deploy.finish_promote` applies that plan in the transaction that records the run: all of it, locked by id, revision and state, or none of it when a change or the live table (`liveFingerprint`) moved on in the milliseconds between, which leaves them Staged and says so. Each address is logged, then the first-publish take-over runs, then the release pushes the live table. Without a list (the AI's approved `propose_deploy_promote`, Settings → Deployments) the click decides: every Staged change the staged build serves.
- **An Owner's production build** (`deploy.trigger` on production) plans, after its publish (so against the files of the build it just made live), the Staged changes of its click and releases them in `deploy.finish_trigger` the same way: the whole plan or none of it.
- **Go live now** (`redirects.go_live_now`): human-only, needs the Publish live permission (`deploy.trigger`), and puts one or more manual changes (Draft or Staged) live at once, all or nothing, then pushes (`trigger: go_live`), also to a target backing off from an earlier failure (`markRedirectsBehind` with `dueNow` ends the wait, the failure count stays). Its result lists every production target: a push that failed, or one `queued` behind a release that holds the live site (its holder pushes when it finishes), means the hosting does not serve the change yet, and the callers say so instead of "live on your site" (Settings shows it as a warning; the approval stands). It holds the live-release lease for its check and write, so no Publish live, rollback or plugin-data build changes the live build or table meanwhile; while one runs, it refuses ("try again in a minute"). `changes` (each id with its revision) binds it to exactly what a card, an approval or a save showed: a change saved since refuses it. It refuses, with the reason and the next step: no pending change, an automatic change (it goes live with its page change), an experiment chat's change, nothing live yet, a from path a live page serves (the page wins, the rule would do nothing), a same-site target the live build does not serve. The AI reaches it only through an approval card: `update_redirect_changes` (`action: "go_live_now"`) or `bulk_create_redirects` (`goLive: "now"`) queue `redirects.propose_go_live`; the card (in the chat, and the queue on Settings → Redirects) approves `redirects.execute_go_live`, wrapped in `requiresApproverPermission(["deploy.trigger"])`, which runs Go live now as the approver, bound to the changes the proposal recorded (id and revision), and marks the proposal applied in the release's own commit: a reject or cancel since the approval read it refuses the release, and a reject after it refuses (`redirects.reject_proposal` reports the proposal's state). A proposal takes as many changes as one tool call saves (500).
- **Rollback** (`deploy.rollback` of production). For every address a live write after the restored run changed (a release, its take-over, a rollback), it reconstructs from the log the live rules the address had as of that run and puts them back, every stored spelling, logging its own write. The change of the newest release that left the address as it is now is Staged again (with that release's origin and owner, no chat's), so it goes live with the next Publish live that ships it; a rollback's own write is no change to re-stage. A rollback to a release an earlier rollback undid therefore brings its redirects back. It skips and reports an address with a newer pending change, and one a Go live now changed since (Go live now's changes stay live). Before it writes, it checks the whole table it leaves for loops (`findRedirectLoops`, as if no page shadowed a rule): a kept Go live now `/b → /a` next to a restored `/a → /b` would be one, and the hosting refuses such a table on every retry. A restoration in a loop is held back, so its address keeps its live rule, and reported.
- **First publish of a page** (below): the release that first ships a page deletes the live rules on its URL.

The scheduler tick and the plugin-data build never apply a pending change (pinned by `scripts/no-automatic-production-deploy.test.ts`, tested in `plugin-data-build.integration.test.ts` and `redirects-publish-live.integration.test.ts`).

### The push to the hosting

Only production is pushed (`SYNC_ENVS`): staging is the staging gateway's. Every change of the live table is followed by its release's push, and nothing of the push runs on a write path (#1254): no page write writes or locks the site-wide `redirect_sync_state` rows, and no provider call runs inside any transaction or under any row lock.

Code: `packages/admin-core/src/deploy/redirect-sync.ts` (model, recording), `StaticPublisher.syncRedirects` (one per provider), `redirect-sync-worker.ts` (the scheduler tick's retry), ops `redirects.sync_provider` / `redirects.sync_status` (`ops/redirect_sync.ts`), migrations `0378_redirect_sync.sql` and `0457_redirect_sync_off_write_path.sql`.

1. A write of a `redirects` row leaves one insert-only row in `redirect_changes` (row triggers of migration 0457, keyed by the writer's transaction id). A release that changed no row leaves nothing.
2. The release runs `syncRedirects` after its run is recorded: Publish live and the plugin-data build in a transaction of their own (#1225), rollback once its run is recorded (#1254, #1250), Go live now after its release commits (`transaction: "none"`). Each run has three steps:
   - **prepare** (one short transaction): fold every visible change row into `wanted_revision` of every production target (and delete it; a row of a transaction still running stays for the next sync); claim the live-release lease by the sync's own id (`deploy_leases.holder_sync_id`), never waiting; read the revision, then the table and the build each target serves.
   - **push** (no transaction): the provider's `syncRedirects` per target. The plan is `buildRedirectPlan` computed against the files of the build the target serves now, so a row whose from path a live page serves is left out (the live page wins). A plan the provider already serves writes nothing (`unchanged`). The claimed lease keeps a Publish live, rollback or another sync from releasing the same channel meanwhile; it is renewed while the push runs and lapses on the database clock if the instance dies.
   - **record** (one short transaction): the attempt, `synced_revision = GREATEST(synced_revision, revision read)`, and the lease release. If more became due during the push, the run takes another round.

   While someone else holds the lease (a Publish live or plugin-data build releasing production #1225, a rollback, another instance's sync), production is skipped and stays behind; the holder pushes it after its run is recorded and the scheduler's retry catches up.
3. Every attempt is recorded (`redirect_syncs`, audit row `redirects.sync_provider`), and a successful one sets `synced_revision`. A failure leaves the target behind (`wanted_revision > synced_revision`). It shows in Settings → Redirects and in the notification bell, the redirect tools' results say "the live redirects are NOT on the hosting yet" with the error, and the scheduler tick retries it with backoff (1 minute, doubling, at most 1 hour). Settings → Redirects also has "Try again now".
4. A served-build change re-pushes the live table (triggers `build`, `publish`, `rollback`): the build carries the table as it was when it was staged.

The update itself creates no pending change: existing rows stay live and visitors see no change. Migration 0682 deletes the sync state of non-production targets, which nothing pushes any more.

No push. | `roles/firebasehosting.admin` on the run SA, which Stage and Publish live already use. |

### gcp-firebase: a cloned version names the current gateway (#1328)

A Hosting version is immutable, so every path that changes what a channel serves without a build creates a new version from the config of one that exists: this redirect sync, the plugin-data release (#1155), Publish live (promote) and rollback. That config carries the `/api/**` Cloud Run rewrite of its day. Contract 16 (#1328) moved the visitor gateway on gcp-firebase from `caelo-<env>-gateway-<suffix>` (now the MCP-Auth-Proxy) to `caelo-<env>-data-gateway` and retired the admin's `run.viewer` on the old service. A verbatim copy then fails, because Hosting checks `run.services.get` on every rewrite target when the version is created ("redirects are saved but do not reach the hosting"), and if it went through it would keep sending visitors' `/api/**` to the proxy.

So every clone passes through `withCurrentGatewayRewrite` (`packages/admin-core/src/deploy/firebase-gateway-rewrite.ts`): the `/api/**` rewrite is replaced by the one the admin's `CAELO_GATEWAY_SERVICE` / `CAELO_GATEWAY_REGION` name, everything else is kept verbatim, and missing env vars fail loudly (no fallback). The redirect sync treats a stale rewrite as a change even when the redirects match, so a sync repoints the live site's `/api/**`. The converge itself does not re-release the live channel (a release outside a recorded run would make the plugin-data build refuse, "released outside Caelo"); instead the admin's first boot after it reads the live release and, when its rewrite is stale, runs one redirect sync of the production targets, which re-releases the served version and moves the recorded location with it (#1380, `refreshStaleLiveReleaseAtBoot`).

The fixed headers (nosniff, the SVG CSP, the favicon type: `packages/admin-core/src/deploy/firebase-version-headers.ts`) take the same path: every clone passes through `withCurrentFixedHeaders`, the redirect sync treats stale fixed headers as a change, and the same boot check runs the sync when the live release's fixed headers are not the current ones. That is how a release that fixes them reaches the live site without a Publish live; the build's own headers (page headers, cache, robots, static-file types) are kept from the version it copies.

What the AI tools report (`bulk_create_redirects`, `bulk_delete_redirects`, `update_redirect_changes`, `_redirect-sync-note.ts`): per saved rule whether staging serves it now, it waits for its target, it is a Draft or it went live after approval; and a production push that failed. `list_unpublished_changes` and `get_publish_gate` list the pending changes going live, waiting for their target and staying in Draft (`redirects.release_plan`). A save never says "live now".

Gates (CLAUDE.md §11.A): saving a rule within the site is routine, one call undoes it. Go live now is a human's click with the Publish live permission, and the AI's Go live now is an approval card. A target on another domain is gated ([below](#a-target-on-another-domain)). An AI `redirects.delete_many` by `matches` that would delete 10 or more rules is refused (`AI_MATCHES_DELETE_LIMIT`). A move of 10 or more URLs is approval-gated (`move_pages`). `redirects.sync_provider` decides nothing (it pushes what is live) and is human/system only.

## A target on another domain

#1358. `to_path` may hold an `https` address, for short links on QR codes and letters, booking links and old subdomains. Such a rule is an open redirect under the site's name, and its source address gets printed, so only one op saves it: `redirects.execute_proposal`, the Owner's click (`settings.write`) on `propose_external_redirect` or on the Settings → Redirects form, which runs the same two ops in one go. The routine ops still refuse anything but a same-site path (`redirectTargetIssue`), so no path around the click exists; serving layers accept both forms (`servableRedirectTargetIssue`). Code: `ops/redirects_pending.ts`, `packages/shared/src/redirect-target.ts`.

The form (`externalRedirectTargetIssue`): `https` only, no credentials, no port, a public host name, and the URL's canonical spelling, so that dot segments, `%2e%2e`, an encoded host and the like are refused and the text on the card is where a browser lands. The host (`externalRedirectHostIssue`) must not be one of this install: site base URL, domains, staging host, `CAELO_SITE_URL`, `CAELO_ADMIN_URL`, `ORIGIN`. All of it is checked at propose, on the card and again at approval, because hosts change while a proposal waits. A from path a static file owns is refused, a rule that replaces another shows on the card, and approval refuses when the rule at that path changed after the proposal. `statusCode` defaults to 302: browsers keep a 301 after the rule is gone.

#1550 — the card names the mode: with the next Publish live (default), or now. An approved rule is a Staged change: staging serves it within seconds and the live site gets it with the next Publish live like any other. "Now" also needs the Publish live permission of the approver (refused before anything is saved otherwise); after the approval commits, Go live now runs as the approver. The plan treats an approved rule like any row: the build wins over it, `redirects.page_conflicts` and `links/redirect-shadows-page` work unchanged, and `to_path` chains end at it.

| Provider | How it is served |
|---|---|
| `gcp-firebase` | `config.redirects[].location` holds the absolute URL. `location` reads `:name` as a capture group, so a colon behind the host goes out as `%3A`. On staging the gateway answers it from `buildRedirectPlan` with a `Location`. |
| `gcp` | A `urlRedirect` path rule with `hostRedirect` and `pathRedirect` (without the latter the load balancer keeps the request's path), one rule and up to two predicates like any redirect, so it counts against the same URL-map quota (#751). `httpsRedirect` stays unset: the API refuses it on a TargetHttpsProxy, and the http URL map has upgraded the request by then. A target with `?query` or `#fragment` is refused at the proposal: the API stores one in `pathRedirect`, but what the load balancer answers has not been verified. |
| self-hosted | The Caddy `map` value is the URL (`redir` takes an absolute target); `_redirects` carries it unchanged. |
| `aws`, `azure` | Refused at the proposal until their publishers exist (#749, #750). `frontDoorRedirectRules` throws on one. The real publishers must lift this deliberately: CloudFront's value can carry a URL, a Front Door rule needs a `customHostname`. |

## No live write as a side effect

#1517, #1550. Nothing a draft or authoring write does changes the live redirects: a save is a pending change, and the live table is written only by the four release paths above. `scripts/no-draft-live-writes.test.ts` pins that: only `redirects/release.ts` writes the `redirects` table, only Publish live, an Owner's production build, a rollback and Go live now run its functions, every save goes through `writeRedirectChanges` from a reviewed list of callers, only the reviewed page ops run the page-move gateway (which leaves out pages only a chat's branch holds and stages what it writes), and only the reviewed sources push the live table. `scripts/no-automatic-production-deploy.test.ts` pins Go live now's callers next to the production build's. `redirects-draft-state.integration.test.ts`, `redirects-publish-live.integration.test.ts` and `draft-no-live-writes.integration.test.ts` prove it end to end. ## A rule on a page's URL

A rule and a page can share a path, in either spelling: a rule answers its path with and without the trailing slash (`redirectFromPathSpellings`), and a table imported from a CMS with `/`-terminated URLs stores `/old/`.

**No provider lets the rule beat a page the build serves.** Every serving layer consumes `buildRedirectPlan`, which leaves such a rule out against the files of the build that target serves (the Firebase version, the live bucket, `current/`, the staged manifest). So the rule answers only while no served build has the page: a page created or published on the draft stays behind its rule on staging until a Stage, and on the live site until Publish live. Then the page answers, and the rule does nothing until the page leaves the build. #1447 was reported as "hosting redirects win over the page"; the staging logs showed the sibling `/de/` page answering 404 in the same second as the `/en/` 301, and both answering 200 after the next Stage: neither page was in the staged build yet.

What keeps the two apart:

- **A move of a main-line page takes the rule over.** `applyPathMoveEffects` stages the removal of the rule on the new URL, in both spellings, before the old URL's 301. The removal waits for its page and goes live with the Publish live that ships the move, so the live site never answers 404 in between (#1521). `move_pages` and slug changes of such a page need no warning: they leave no rule on it.
- **A page only a chat's branch holds has no redirect effects (#1517).** A page created or duplicated in a chat (`chat_branch_id` set until the merge takes it to main) is served nowhere outside that chat's preview. A move of it (`create_variant` gives a copy its locale prefix, a slug change, a nested child following its parent) only stores the path: no removal of the rule on the new URL, which keeps answering on the live site; no 301 from the old path, which was never public; no chain repointing. The merge (Stage) keeps it that way: a page that only now joins main gets its path and nothing else (`refreshLivePathsAfterMerge`).
- **Publish live takes the URL over for a page it ships for the first time (#1517).** The release that stamps a page's `first_published_at` (`deploy.finish_promote`, and an Owner's direct production build in `deploy.finish_trigger`) deletes every live rule on that page's path, in both spellings, in the same transaction, after it released the Staged changes (`takeOverRedirectsOnFirstPublishedPages`, logged as `take_over`), and the release's push sends the table. A pending removal at that address is fulfilled and dropped with it: nothing is left to remove. Not at the merge: the live site serves the previous build until Publish live. Until then the plan already lets the staged page win on staging, and the rule answers on the live site, which does not have the page yet. The 404 page is left out. A page that was live before and comes back (unpublished, then published again) is not taken over: that pair is the writer's to settle.
- **Other writes say so.** A page that lands next to a rule (`build_page`, `duplicate_page`, `create_variant`) or goes to published (`set_pages_status_many`), a rule written onto a page's path (`bulk_create_redirects`, Settings → Redirects): the result names the rule with its state (a pending one says Staged or Draft), the page and the next step, read from `redirects.page_conflicts`, which sees the rules as they stand once their pending changes are live. For a page that was never live (`pageLive: false`) the next step is nothing: Publish live takes the URL over; for a live rule, deleting it early would leave the live URL answering 404 until then, and to keep the rule the page gets another slug. For a page that was live before, the rule is to be deleted or the page moved. The op sees pages as the caller's chat does (`pages.list`, pending renames, moves and deletes included), leaves the 404 page out, and stays O(request).
- **A Stage reports what is left.** `links/redirect-shadows-page` is an error ([quality checks](../quality-checks.md)) for a rule on the URL of a page that was live before, computed in the `links` check against the staging view (`redirects.release_plan` with `includeRows`: the live rows with the Staged changes the staged build serves). On a page that was never live it is `links/redirect-taken-over`, an info: Publish live settles it. The check also reports a page staging really answered with a redirect (`StagedPage.redirectedTo`) as the error, which the plan should make impossible and which would otherwise pass: the fetched HTML is then the target's, and every other check reads that.

## Global settings: classification

"Provider / runtime" settings are read where the site is served, so a save is the sync. "Rendered" settings are baked into the build. They are stored live (not on the chat's branch) and reach production only with the next Stage + Publish live: Publish live copies the staged build (#1330), and a staged build rendered for another origin than the live site's is refused with "Stage again". With #1154 nothing else builds production. Making them branch-aware draft state is #1158.

| Setting | Op(s) | Class | How it goes live | Approval (§11.A) |
|---|---|---|---|---|

The rendered settings stored on `site_defaults` are part of the render fingerprint (`ops/quality/render-fingerprint.ts`, `setting:<column>` keys): an Owner's direct production build is refused when one changed after the last Stage, so a setting never reaches production unaudited (#1497). Publish live copies the staged build and needs no such check. A setting that renders nothing (site name, purpose, design brief, the default layout, the media CDN threshold while the copy is off) is not compared and forces no Stage. A Stage from before the keys existed recorded none, so the first direct production build after that update is refused once, with that reason; one new Stage records them.

**Home and 404 page from a chat (#1497).** Both designations are global until #1158 makes them draft state. `home_page_id` and `not_found_page_id` name main pages only, because main's build reads them. A chat designating a main page moves the pointer at once, and for the home page main's stored `current_path` too (`recomputeOwnedCurrentPaths`): the designation is no pending change, so no merge would recompose those paths, and the next Stage from any chat carries it. A chat designating a page only its branch holds writes `pending_home_page_id` / `pending_not_found_page_id` instead. That branch reads it as its designation (`loadSiteDesignations`), everyone else keeps the current home and 404 page, and the merge that takes the page live moves it into the pointer before replaying the page (`claimPendingDesignations`), so the old home has left `/` when the new one joins main. A home change writes no 301, from a chat or not: the root changes page, no URL is retired. There is one pending slot per designation: the latest call wins.

Static files (`static_files.*`, #1461) are not settings either: they are stored in Caelo and reach a site only as files of a Stage build, so a save changes nothing until a Stage and Publish live ([static-files.md](./static-files.md)).

Themes, layouts, templates, content instances, lists and plugin rows are not global settings in this sense: they are already draft state that goes live with Stage + Publish live.
